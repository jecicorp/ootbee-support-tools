# Dependency Vulnerability Scanning

How `ootbee-support-tools` detects known CVEs in its dependencies, and why the
pipeline blocks on some of them and not others.

## Why two perimeters

This repository builds two **AMPs**: `repository` (`support-tools-repo`,
installed in the Alfresco repository) and `share` (`support-tools-share`,
installed in Alfresco Share). An AMP only packages `compile` scope
dependencies; everything else - Alfresco, Share, Spring Framework, Surf,
log4j, the servlet API - is `provided` by the ACS and Share images at runtime.

Listing the `lib/` folder of the AMPs last built locally (version
`1.2.3.2-PY.2`) confirms it: seven JARs in the repository AMP, six in the Share
AMP.

| AMP | JAR | Origin |
|---|---|---|
| repository | `cron-utils` | declared in `repository/pom.xml` |
| repository | `javassist`, `javax.el` | transitive dependencies of `cron-utils` |
| repository | `time4j-core`, `time4j-i18n` | declared in `repository/pom.xml` |
| repository | `support-tools-repo-*-classes` | our own code |
| share | `commons-compress` | declared in `share/pom.xml` |
| share | `commons-codec`, `commons-io`, `commons-lang3` | transitive dependencies of `commons-compress` |
| share | `support-tools-share-*-classes` | our own code |

So the `compile` perimeter is the AMP payload: what we ship and therefore own.
The `provided` perimeter is the Alfresco and Share platform, which this
repository cannot fix.

| SBOM | Scopes | Contents | Gate |
|---|---|---|---|
| `target/bom-runtime.json` | `compile` | Payload of both AMPs | **Fails the pipeline on CRITICAL** |
| `target/bom-full.json` | `compile` + `provided` | The above plus the Alfresco and Share platform | Reported, never blocking |

Scanning both perimeters as one would make the report unreadable and the gate
useless: the full tree carries dozens of HIGH/CRITICAL findings that are
remediated on the platform side, not by anything under `src/`.

The `provided` versions come from the `acs-community-packaging` BOM imported at
`alfresco.platform.version`, which is still `6.1.2-ga` in the root `pom.xml`
(the `acs-docker-*` profiles only change the Docker images of the test stack).
The full report therefore describes ACS 6.1 libraries, not the ACS release the
AMPs are actually installed on.

## Running it locally

```bash
mise run audit        # blocking gate, same as CI
mise run audit:full   # full runtime tree, HIGH + CRITICAL, informative
mise run sbom         # regenerate both SBOMs only
```

`mise` provides both Maven and the Trivy version pinned in `mise.toml`. That
version is kept in sync with the image tag used by the `dependency-scan` job in
`.gitlab-ci.yml`, itself mirrored in `images-docker/sync-images-docker/sync.yaml`.

## How it works

SBOMs are generated by the CycloneDX Maven plugin, declared in the root
`pom.xml` under `<pluginManagement>` and **not bound to any lifecycle phase** -
a normal `mvn install` is unaffected. It is invoked explicitly:

```bash
mvn org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom \
    -DoutputFormat=json -DoutputName=bom-runtime \
    -DincludeProvidedScope=false -DincludeTestScope=false
```

> The plugin's user properties have **no `cyclonedx.` prefix** (`-DoutputName`,
> not `-Dcyclonedx.outputName`). Getting this wrong silently produces a default
> `bom.json` with every scope included - the scan then reports on the wrong
> perimeter without failing.

The plugin configuration sets `skipNotDeployed` to `false`. The root `pom.xml`
sets `maven.deploy.skip=true` (only the `ci` profile turns it off), and by
default the plugin skips every module that is not deployed: without that
setting `makeAggregateBom` logs "Skipping CycloneDX goal" and writes no file.

`makeAggregateBom` walks the reactor, so it needs no prior build: the modules
resolve from the reactor itself rather than from an installed artefact. The
goal refuses to run with `-o` (offline).

Trivy then scans the SBOMs. It needs no NVD API key, unlike OWASP
dependency-check, which is why it was chosen here.

## CI

No pipeline runs on `stable`: a release is built and published by the pipeline
of its tag. Stage `security`, between `build` and `deploy`, runs on `develop` and
on tags:

- **`sbom`** (Maven image) - generates both SBOMs, published as artifacts.
- **`dependency-scan`** (Trivy image) - scans them. The full report is printed
  first for context, then the runtime SBOM is re-scanned with `--exit-code 1
  --severity CRITICAL`. Raw JSON reports are kept as artifacts (`when: always`).

`maven-deploy` lists `dependency-scan` in its `needs`. This is what makes the
gate real: jobs using `needs` start as soon as their listed dependencies succeed
and otherwise **ignore preceding stages entirely** - without that line, a deploy
would proceed over a failed scan. For the same reason `maven-deploy` also lists
`maven-build` (with its artifacts): declaring `needs` drops the implicit wait on
the `build` stage, so the build has to be named explicitly to keep a failed
build from being deployed.

The Trivy vulnerability database is cached under `.trivycache/` with its own
cache key, which overrides the global `.m2` cache for that job.

## Release SBOM

On a tag, once `maven-deploy` has published the release, `sbom-publish`
publishes the two SBOMs the gate scanned to the Jeci Nexus next to it, with
`deploy:deploy-file`:

| File | Classifier |
|---|---|
| `bom-runtime.json` | `cyclonedx` |
| `bom-full.json` | `cyclonedx-full` |

The two `deploy-file` executions (`sbom-runtime`, `sbom-full`) and the
`sbom.repository.id` / `sbom.repository.url` properties are declared in the `ci`
profile of the root `pom.xml`, the profile that points `<distributionManagement>`
at `pristy-releases`; the job therefore runs with `-Pci`, like `maven-deploy`.
The executions have `<phase>none</phase>`, so `mvn deploy` never runs them, and
the pom version at the tag must be a release version. A dry run against a local
folder:

```bash
mise run sbom
mvn -Pci -N deploy:deploy-file@sbom-runtime deploy:deploy-file@sbom-full \
    -Dsbom.repository.id=local -Dsbom.repository.url=file:///tmp/fake-nexus
```

A released version can then be re-scanned at any time against the current
vulnerability database, from its published SBOM.

## Remediating a finding

**In the runtime SBOM** (blocking) - it is our dependency:

- A finding in the repository AMP is fixed in `repository/pom.xml`: bump
  `cron-utils` or `time4j`, or pin the transitive artefact (`javassist`,
  `javax.el`) in its `<dependencies>`.
- A finding in the Share AMP is fixed in `share/pom.xml`, where
  `commons-compress` is pinned in `<dependencyManagement>`; its `commons-*`
  transitive dependencies can be pinned the same way.

**In the full SBOM** (informative) - it belongs to the platform. Two options, in
order of preference:

1. Bump `alfresco.platform.version` (and `alfresco.share.version`) in the root
   `pom.xml`, so that the report at least reflects a supported ACS release.
2. Override the JAR in the platform Docker image. Note that `alfresco-mmt`
   **never overwrites** a JAR already present in the platform, it only adds - so
   shipping a newer version through an AMP does not work.

A `<dependencyManagement>` pin in the root `pom.xml` (as done for `slf4j-api`
and `log4j-core`) only constrains compilation. It does not change which JAR
Alfresco loads at runtime.

## Not covered here

This scans Java dependencies only. CVEs in Tomcat, the JRE and the OS packages
of the ACS and Share images are found with `trivy image` against those images,
which belongs to the image build pipeline rather than to this dependency scan.
The JavaScript and FreeMarker resources shipped in the AMPs are not scanned
either.
